# Snapshot Library Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A library over the snapshot files: browse everything you have saved, search it, filter it by kind, category, rating and tags, and save into it by default.

**Architecture:** The metadata lives *in* each snapshot file, so a file carries its own notes when it is copied or sent. The format is reshaped first, to version 3: the parameter data nests by address and by the parameter path's own separator, which makes a file about a third of its size and genuinely diffable, and the metadata is written before it so a browse can read a file's head and stop. The in-memory model and the restore service are untouched — only the serialization changes. A library is one folder, remembered between sessions in the application's first settings file.

**Tech Stack:** C# / .NET 10, Avalonia 12, ReactiveUI, NUnit, System.Text.Json.

---

## What was decided, and why

**Metadata in the snapshot file**, not sidecars and not one index. A file then carries its own name, category, tags, notes, rating and favourite flag wherever it goes; there is one thing to back up; and nothing goes stale when files are added or removed outside the application. The costs are real and accepted: editing a note rewrites a file that also holds every parameter value (safe — the existing save is atomic), and browsing has to read every file (addressed below).

**The category is Roland's own.** `Integra7Preset` already parses the instrument's 34 tone categories — Ac.Piano, Organ, E.Guitar, Strings, Synth Lead, Drums, FX and the rest — and the preset grids already show them. Inventing a second vocabulary beside one the user already knows would be the wrong kind of new. This is also what modern preset browsers do (Kontakt, Arturia, u-he, Zenology): a fixed vocabulary for reliable filtering, free text for everything else. **Free tags are the second axis**, for what a category cannot say ("for the trio gig", "needs less bark"). **A rating of 0 to 5 stars** is the third.

**A Studio Set gets no category.** It is sixteen parts, each with its own; there is no single tone category for it. It is filtered by kind, by tags and by rating like everything else. If a Studio Set vocabulary turns out to be wanted (Live, Session, Church, Template) it is one list added later, not a decision to force now.

**One library folder, chosen once, remembered.** This application persists nothing between sessions today, so this introduces its first settings file. That is a real addition and is scoped tightly: one file, one folder path in it, and a default under the user's Documents when it is missing or unreadable.

**Both save paths stay.** Save Studio Set and Save Tone default to the library, with a name, category, tags and rating; the existing file dialogs remain for exporting a snapshot anywhere else and for importing one from anywhere. Nothing that works today stops working.

**The bulk dump is not in this plan.** The roadmap is explicit that reading every user Studio Set and user tone slot into the library is "the part with real device risk — hundreds of reads, and writes into user memory" and "wants its own plan and a dry-run mode". The numbers agree: 32 user drum kits at 92 blocks each, 256 user PCM synth tones at 8, plus the SuperNATURAL engines, plus 64 Studio Sets at 53. Thousands of answered reads. It gets its own plan once this lands.

## The file format changes first

**No v1 or v2 files exist outside this machine** — confirmed by the user — so there is nothing to stay
compatible with, and the format is reshaped before anything is built on it. `CurrentFormatVersion` goes
to **3** and earlier versions are refused, which is now honest rather than a hazard.

**The parameter data becomes path-shaped.** Today every value is an object repeating three keys and a
path prefix:

```json
"Domains": [
  { "Start": "Temporary Studio Set", "Offset": "Offset/Not Used", "Offset2": "Offset2/Studio Set Common",
    "Values": [
      { "Path": "Studio Set Common/Studio Set Name", "Value": "Old Set", "Raw": null },
      { "Path": "Studio Set Common/Studio Set Tempo", "Value": "120", "Raw": 120 } ] } ]
```

Nested by the addresses and then by the parameter path's own `/`:

```json
"Blocks": {
  "Temporary Studio Set": {
    "Offset/Not Used": {
      "Offset2/Studio Set Common": {
        "Studio Set Common": {
          "Studio Set Name": "Old Set",
          "Studio Set Tempo": [120, "120"]
        } } } }
}
```

Measured on a real 53-block Studio Set capture of 1,502 values: **196KB and 7,889 lines become 73KB and
1,784** — 2.7× smaller. (This paragraph originally guessed 4,000 values and 400KB; Task 0 measured it and
the guess was double. The ratio was about right.) And it is diffable in the way the format was always
meant to be: a changed tempo is one changed line under a heading that says where it is.

**Two consequences, and the first is the dangerous one.**

**Order must survive.** `StudioSetSnapshotService.RestoreAsync` depends on values arriving in address
order, because a discriminator has to be applied before the parameters that only exist under its value —
a chorus type before that type's knobs. Today an ordered `List<SnapshotValue>` guarantees it. A JSON
object has no ordering guarantee and **`Dictionary<string, …>` does not contract one either**: it happens
to preserve insertion order until something is removed, which is exactly the kind of accidental
correctness that breaks silently and late. So the reader must walk the document in document order, and
that is pinned by a test rather than by a comment.

**A leaf carries two values.** `Raw` is what a restore actually writes — it survives this build renaming
an enum string — and the display value is what makes the file readable, which is the point of the format.
So a leaf is `[raw, "display"]` for anything numeric or discrete, and a bare `"string"` for a text
parameter, which has no raw form at all. Two shapes, one branch to read them.

**The in-memory model does not change.** `Integra7Snapshot` keeps its ordered
`List<SnapshotDomain>`/`List<SnapshotValue>`, and `StudioSetSnapshotService` — hardware-verified, and
carrying most of the reasoning that keeps a restore correct — is not touched at all. Only the
serialization changes, through a converter. That is what makes this a small change rather than a
frightening one.

### Task 0: Reshape the file

**Files:**
- Modify: `Src/Models/Services/Integra7Snapshot.cs`
- Create: `Src/Models/Services/SnapshotJson.cs` (the converter)
- Test: `Tests/TestSnapshotJson.cs`

**Read `Src/Models/Services/Integra7Snapshot.cs` and `StudioSetSnapshotService.cs` in full first.** The
service is hardware-verified and its comments carry why a restore is correct; **you are not changing it**,
and if you find yourself needing to, stop and say so.

- [ ] **Step 1: Write the failing tests**

`Tests/TestSnapshotJson.cs`. The ones that matter:

- **Order survives a round trip.** Build a snapshot whose values are deliberately *not* in alphabetical
  order — a discriminator first and a dependent second, e.g. `Chorus Type` then `Chorus Parameter 1` —
  serialize, deserialize, and assert the values come back in the order they went in, block order too.
  This is the test the whole task exists for: `RestoreAsync` applies values in file order and a
  discriminator arriving second is a restore that writes a value nobody asked for.
- **The shape is nested**, and `Blocks` is written last: assert the JSON contains
  `"Offset2/Studio Set Common"` nested under `"Offset/Not Used"` nested under `"Temporary Studio Set"`,
  and that every metadata property appears before `"Blocks"`.
- **A leaf carries both values**: a numeric parameter round-trips its raw *and* its display string; a
  text parameter (`Raw` null) round-trips as a bare string and comes back with `Raw` null.
- **A path with more than one `/` nests further**, and a path with none is a single leaf. Do not assume
  every path is two segments — assert whatever the parameter database actually contains, and say what you
  found.
- **Two parameters sharing a prefix land in one object**, and both survive.
- **Version 2 is refused**, naming the version, exactly as version 1 already is.
- **A duplicate key** — the same path twice in one block, which a hand-edited file can contain — is
  refused rather than silently keeping the last one. A snapshot that quietly drops a value is worse than
  one that will not open.

- [ ] **Step 2: Write the converter**

A `JsonConverter<Integra7Snapshot>` in `SnapshotJson.cs`, used by `ToJson`/`FromJson`. Write with a
`Utf8JsonWriter`; read with `Utf8JsonReader`, which reads in document order by construction — **do not
deserialize the blocks into a `Dictionary`**, for the reason above.

`CurrentFormatVersion` becomes 3. The existing refusal message already names the version it found and the
version this build reads, so it needs no change beyond the constant.

Keep every validation `FromJson` already performs — the null checks, the `Kind` check, the tone-type
check — and their comments, which explain what each one is protecting against. They are about the values,
not about the shape, so they survive the reshaping unchanged.

- [ ] **Step 3: Run the whole suite**

Everything that reads or writes a snapshot must still pass: `TestStudioSetSnapshot`, `TestApplyRawValue`
and anything else touching the format. **If a test outside your new fixture fails, that is the signal to
read it rather than to adjust it** — say which and why before changing anything.

### Task 1: The metadata on the file

- [ ] **Step 1: Write the failing tests**

Create `Tests/TestSnapshotMetadata.cs`:

```csharp
using System.Collections.Generic;
using Integra7AuralAlchemist.Models.Services;

namespace Tests;

public class SnapshotMetadataTests
{
    private static Integra7Snapshot Minimal() => new(
        Integra7Snapshot.CurrentFormatVersion, "Warm Rhodes",
        [new SnapshotDomain("Temporary Tone Part 1", "Offset/Temporary SuperNATURAL Synth Tone",
            "Offset2/SuperNATURAL Synth Tone Common",
            [new SnapshotValue("SuperNATURAL Synth Tone Common/Tone Name", "Warm Rhodes", null)])],
        SnapshotKinds.Tone, "SN-S");

    [Test]
    public void A_snapshot_saved_without_metadata_reads_as_empty_rather_than_null()
    {
        // Every snapshot the application writes carries all five, but a file can be written by hand and
        // the library reads whatever is in the folder. Absent means empty, never null: the alternative is
        // a null check at every reader, and the one that gets forgotten is a crash while listing a folder.
        var written = Integra7Snapshot.ToJson(Minimal());
        var read = Integra7Snapshot.FromJson(written);

        Assert.That(read.Category, Is.EqualTo(""));
        Assert.That(read.TagList, Is.Not.Null.And.Empty);
        Assert.That(read.Notes, Is.EqualTo(""));
        Assert.That(read.Rating, Is.EqualTo(0), "0 is unrated");
        Assert.That(read.Favourite, Is.False);
    }

    [Test]
    public void Metadata_survives_a_round_trip()
    {
        var written = Minimal() with
        {
            Category = "E.Piano", Tags = ["warm", "trio gig"], Notes = "less bark", Rating = 4,
            Favourite = true,
        };

        var read = Integra7Snapshot.FromJson(Integra7Snapshot.ToJson(written));

        Assert.That(read.Category, Is.EqualTo("E.Piano"));
        Assert.That(read.Tags, Is.EqualTo(new[] { "warm", "trio gig" }));
        Assert.That(read.Notes, Is.EqualTo("less bark"));
        Assert.That(read.Rating, Is.EqualTo(4));
        Assert.That(read.Favourite, Is.True);
    }

    [Test]
    public void Every_piece_of_metadata_is_written_before_the_parameter_data()
    {
        // So a browse can read a file's head and stop. A drum kit snapshot is 92 blocks of values; with
        // the blocks written first, listing a library would mean parsing all of it, per file, to find a
        // name. This is the property SnapshotHead depends on and nothing else enforces. Task 0's fixture
        // pins that Blocks is last; this pins that each metadata property is before it, so adding a sixth
        // and forgetting its order fails here.
        var json = Integra7Snapshot.ToJson(Minimal() with { Category = "E.Piano", Rating = 5 });

        var blocks = json.IndexOf("\"Blocks\"", System.StringComparison.Ordinal);
        Assert.That(blocks, Is.GreaterThan(0));
        foreach (var property in new[] { "FormatVersion", "Name", "Kind", "ToneType", "Category", "Tags",
                     "Notes", "Rating", "Favourite" })
            Assert.That(json.IndexOf($"\"{property}\"", System.StringComparison.Ordinal),
                Is.GreaterThan(0).And.LessThan(blocks), $"{property} must be written before Blocks");
    }

    [Test]
    public void A_rating_outside_zero_to_five_is_refused()
    {
        // The star control cannot produce one, but a hand-edited file can, and a five-star filter that
        // silently missed a seven-star entry would be a puzzle rather than an error.
        var json = Integra7Snapshot.ToJson(Minimal()).Replace("\"Rating\": 0", "\"Rating\": 7");
        Assert.That(() => Integra7Snapshot.FromJson(json), Throws.TypeOf<SnapshotFormatException>());
    }
}
```

### Task 2: Reading a file's head

**Files:**
- Create: `Src/Models/Services/SnapshotHead.cs`
- Test: `Tests/TestSnapshotHead.cs`

Listing a library must not parse every parameter of every file. Tasks 0 and 1 put the metadata before
`Blocks`; this reads up to `Blocks` and stops.

- [ ] **Step 1: Write it**

A `Utf8JsonReader` over the file's bytes, reading top-level properties into a small record and returning
as soon as it reaches `Blocks`. Shape:

```csharp
/// <summary>What a library list needs from a snapshot file: everything except the parameter data.</summary>
public sealed record SnapshotHead(string Name, string Kind, string? ToneType, string Category,
    IReadOnlyList<string> Tags, string Notes, int Rating, bool Favourite);
```

with `public static SnapshotHead? TryRead(Stream json)` returning null for anything that is not a
snapshot — a stray file in the folder must be skipped, not throw.

**Why a reader and not `JsonDocument`:** `JsonDocument.Parse` materialises the whole file, which for a
drum kit snapshot is the thing this class exists to avoid. Read forward, stop at `Blocks`, never touch
its contents.

**What it must not do:** validate. `FromJson` is where a file is judged; this is a listing. A file whose
rating is 7 still appears in the list — it fails when it is opened, with the message `FromJson` gives,
and that is one place to be wrong instead of two.

- [ ] **Step 2: Tests**

At least: a file with all the metadata read correctly; a file with none of it (empty category, no tags,
rating 0); **a file whose `Blocks` comes first anyway** — a hand-edited one — which must still work by
reading past it, because writing the metadata first is a convention of ours and not a rule of JSON, and
this is the difference between an optimisation and a requirement; a text file that is not JSON, returning
null; and an empty file, returning null.

- [ ] **Step 3: Run and commit**

```bash
git commit -m "feat: read a snapshot's metadata without its parameter data"
```

**Files:**
- Create: `Src/Models/Services/SnapshotLibrary.cs`, `Src/Models/Services/LibraryFilter.cs`
- Test: `Tests/TestLibraryFilter.cs` (and library enumeration over a temp folder)

`SnapshotLibrary`: enumerate a folder's `*.json` into entries (path, head, file date), skipping anything
`SnapshotHead.TryRead` refuses; and write metadata back into an existing file — read it with `FromJson`,
apply the metadata with `with`, write it atomically. **Editing a note must not rewrite the parameter

`LibraryFilter`: pure, and this is where the tests are. Given the entries and a filter — free text, kind,
category, minimum rating, favourites-only, and a set of tags — return what is admitted. Rules worth
pinning:

- Free text matches name, notes, category **and** tags, case-insensitively. A user typing "rhodes" does
  not know or care which field it was in.
- An empty filter admits everything, including unrated and untagged entries. A "minimum rating" of 0
  must not mean "only unrated".
- Tags are AND, not OR: choosing "warm" and "gig" means both. This is the one a user will assume either
  way, so it is written down and tested rather than left to be discovered.
- Category filtering is exact, because the vocabulary is fixed. A Studio Set has no category and is
  admitted by "any category" only.

## Known limitations to state in the commit messages

- **Editing metadata rewrites the whole file.** It holds the parameter data too. The write is atomic, so
  a failure cannot destroy what was there, but a library on a slow network drive will feel it.
- **The library is one folder, not a tree.** Sub-folders are not enumerated. If that turns out to be how
  a large library wants to be organised, it is a change to one method.
- **No bulk dump.** Reading every user slot into the library is a separate plan, for the reason the
  roadmap gives: hundreds of reads and writes into user memory, wanting a dry-run mode.
- **A Studio Set has no category**, only tags and a rating.
- **Nothing watches the folder.** A file added by another application appears when the list is refreshed,
  not before.
