# Layer Map Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Layers tab showing all sixteen parts' key and velocity ranges on one chart, draggable, so splits and layers are visible and adjustable at a glance.

**Architecture:** One lane per part, key left-to-right across the lane, and the part's velocity range drawn as the box's vertical extent *within* its own lane — so both dimensions are on one chart and which parts answer a given key is read straight down a column. An owner-drawn control takes an immutable list of zone snapshots and raises events for edits; the view model holds the live parameter wrappers. All eight range parameters per part live in `Studio Set Part`, which is read at startup, so the page costs no reads.

**Tech Stack:** C# / .NET 10, Avalonia 12, ReactiveUI, NUnit.

---

## What is already here, and what is not

**`PmtZoneMapping` is reusable and this plan uses it.** `Src/Models/Services/PmtZoneMapping.cs` is pure — no
Avalonia — and gives `KeyToX`, `XToKey`, `VelToY`, `YToVel`, `ToRect` and `HitRect` returning
`None`/`Body`/`Left`/`Right`/`Top`/`Bottom`. It has tests. The roadmap said `PmtZoneEditorControl` could be
reused for this; that is wrong — the control is four zones as sixteen individual styled properties — but the
*mapping under it* is exactly right, and `PmtZoneEditorControl` is the drawing and dragging idiom to copy
(`Render`, `OnPointerPressed`/`Moved`/`Released`, a `_dragZone`/`_dragHandle`/`_dragOrigPos` triple).

**All the data is in memory.** `Keyboard Range Lower`/`Upper`, `Keyboard Fade Width Lower`/`Upper`,
`Velocity Range Lower`/`Upper` and `Velocity Fade Width Lower`/`Upper` are all in `Studio Set Part`
(`StudioSetPartEditorViewModel.cs:150`-`157`), and every part's block is read at startup. No reads, no load
state — the same position the mixer was in.

**`MidiNote`** (`Src/Models/Services/MidiNote.cs`) gives `Name`, `IsBlack`, `IsC` for the key axis.

**`PointerGesture`** (`Src/Controls/PointerGesture.cs`) is how a drag becomes one undo step. **Use it. Do not
write pointer-capture handling from scratch** — the last plan that specified it from scratch got it wrong, and
the memory note `pointer-capture-lost-is-direct` exists because of that. `PointerCaptureLostEvent` is Direct
and reaches only the element that held the capture.

**Decisions taken with the user:**

- **Lanes with velocity as box height.** One row per part.
- **Fade widths are drawn but not dragged**, *and the map offers navigation to the controls that edit them* —
  the four fade knobs are on the part's own Set Part tab.
- **A new top-level tab**, after Mixer: Parameters, Mixer, Layers, Motional Surround, SRX Loader.
- **A click selects the part and shows its four numbers**; **double-click opens the part's tab**; and **a click
  auditions the note under the pointer** on that part.

**The audition's velocity comes from the pointer's Y within the lane** — the same mapping that draws the box
height. Clicking low in a lane plays soft, high plays loud, and clicking a spot the part's box does not cover
is *silent*. That is the map answering "does this part respond here?", not a defect, and the plan says so
because it will otherwise be reported as one.

## How much of this plan is literal code, and why not all of it

Task 1 gives every line, because it is pure and I can reason about it completely. Tasks 2 to 5 give
requirements, the reasoning behind each, the traps by name, and the exact file to copy the idiom from — but not
three hundred speculative lines of `Render`.

That is a deliberate departure from "complete code in every step", and the mixer is the argument for it: the
draft XAML in that plan needed six corrections on contact with the real view models, one of which
(an implicit `DataTemplate` losing to `App.axaml`'s `ViewLocator`) I had no way to foresee, and the one piece I
*did* specify line-by-line without a precedent to copy — the slider's capture-lost handling — was the only
outright bug in the branch. Pointing at working code beats inventing plausible code that cannot be compiled
while the plan is being written.

So: where this plan says "read X first", that is not a suggestion, it is the specification.

Create `Src/Models/Services/LayerMapGeometry.cs`. `LayerZone` lives here rather than in the control because the
geometry is what consumes it and the tests need it without Avalonia:

```csharp
using System;
using System.Collections.Generic;

namespace Integra7AuralAlchemist.Models.Services;

/// <summary>One part's zone, as the layer map draws it: an immutable snapshot, not a live view model. The
/// control takes a list of these and knows nothing else about the application — which is what keeps the
/// drawing and hit-testing testable, and what lets the view model own the parameter wrappers.</summary>
/// <param name="PartNo">Zero-based.</param>
/// <param name="Label">What to write on the zone: the part number.</param>
/// <param name="ToneName">The patch the part holds, drawn after the label when there is room.</param>
public readonly record struct LayerZone(
    int PartNo,
    int KeyLo, int KeyHi,
    int VelLo, int VelHi,
    int KeyFadeLo, int KeyFadeHi,
    int VelFadeLo, int VelFadeHi,
    string Label, string ToneName);

/// <summary>Where the layer map draws things and what is under the pointer. Pure, and built on
/// <see cref="PmtZoneMapping"/> rather than re-deriving it: the key axis is the same axis the PMT zone editor
/// uses, and velocity is that editor's Y mapping applied within one lane instead of the whole chart.
///
/// Sixteen lanes, part 1 at the top. A lane spans the full key range; a zone occupies part of its lane
/// horizontally by key and vertically by velocity, so which parts answer a given key is read down a column
/// and how loudly each answers is read within its own row.</summary>
public static class LayerMapGeometry
{
    /// <summary>Lanes, one per part.</summary>
    public const int Lanes = Constants.NO_OF_PARTS;

    /// <summary>The whole of one part's row.</summary>
    public static PmtZoneMapping.Rect LaneRect(int part, double w, double h)
    {
        var laneH = h / Lanes;
        return new PmtZoneMapping.Rect(0, part * laneH, w, laneH);
    }

    /// <summary>Which part's lane contains <paramref name="y"/>, or null when the point is off the chart.
    /// Null rather than clamped: a pointer that leaves the chart must stop the drag it was doing, not carry on
    /// editing the nearest part.</summary>
    public static int? LaneAt(double y, double w, double h)
    {
        if (h <= 0 || y < 0 || y >= h) return null;
        var lane = (int)(y / (h / Lanes));
        return lane < 0 || lane >= Lanes ? null : lane;
    }

    /// <summary>The rectangle a zone occupies: its key range horizontally, its velocity range vertically
    /// within its own lane, loud at the top.</summary>
    public static PmtZoneMapping.Rect ZoneRect(int part, int keyLo, int keyHi, int velLo, int velHi,
        double w, double h)
    {
        var lane = LaneRect(part, w, h);
        var x = PmtZoneMapping.KeyToX(Math.Min(keyLo, keyHi), w);
        var x2 = PmtZoneMapping.KeyToX(Math.Max(keyLo, keyHi), w);
        // VelToY over the lane's own height, then offset into the lane.
        var yTop = lane.Y + PmtZoneMapping.VelToY(Math.Max(velLo, velHi), lane.H);
        var yBot = lane.Y + PmtZoneMapping.VelToY(Math.Min(velLo, velHi), lane.H);
        return new PmtZoneMapping.Rect(x, yTop, x2 - x, yBot - yTop);
    }

    /// <summary>The velocity <paramref name="y"/> names within <paramref name="part"/>'s lane. The same Y in
    /// a different lane is a different velocity, which is what makes a lane a lane.</summary>
    public static int VelocityAt(int part, double y, double h)
    {
        var lane = LaneRect(part, 0, h);
        return PmtZoneMapping.YToVel(y - lane.Y, lane.H);
    }

    /// <summary>The key <paramref name="x"/> names. A straight pass-through, here so a caller never has to
    /// mix the two mapping classes.</summary>
    public static int KeyAt(double x, double w) => PmtZoneMapping.XToKey(x, w);

    /// <summary>What is under the pointer: which part's lane, and which part of that part's zone.
    ///
    /// The part comes from the lane, not from the zone, so a point inside a lane but outside that part's zone
    /// still names the part with <c>Handle.None</c>. That is deliberate and load-bearing: clicking an empty
    /// spot in a lane auditions *that part* at that key and velocity and hears nothing, which is how the map
    /// answers "does this part respond here?".</summary>
    public static (int? Part, PmtZoneMapping.Handle Handle) HitTest(double x, double y,
        IReadOnlyList<LayerZone> zones, double w, double h, double margin)
    {
        var lane = LaneAt(y, w, h);
        if (lane is not { } part) return (null, PmtZoneMapping.Handle.None);

        foreach (var z in zones)
        {
            if (z.PartNo != part) continue;
            var r = ZoneRect(part, z.KeyLo, z.KeyHi, z.VelLo, z.VelHi, w, h);
            return (part, PmtZoneMapping.HitRect(x, y, r, margin));
        }

        return (part, PmtZoneMapping.Handle.None);
    }

    /// <summary>How wide a fade is, in pixels. A fade width is a span of keys or of velocity steps, so its
    /// pixels are that span's pixels — which is why these are widths and not positions.</summary>
    public static double KeyFadeLowerWidth(LayerZone z, double w) => PmtZoneMapping.KeyToX(z.KeyFadeLo, w);

    public static double KeyFadeUpperWidth(LayerZone z, double w) => PmtZoneMapping.KeyToX(z.KeyFadeHi, w);

    public static double VelFadeLowerHeight(LayerZone z, double h)
    {
        var laneH = h / Lanes;
        return laneH - PmtZoneMapping.VelToY(z.VelFadeLo, laneH);
    }

    public static double VelFadeUpperHeight(LayerZone z, double h)
    {
        var laneH = h / Lanes;
        return laneH - PmtZoneMapping.VelToY(z.VelFadeHi, laneH);
    }
}
```

Note `VelocityAt` calls `LaneRect(part, 0, h)` — the width is irrelevant to a Y question, and passing 0 says
so.

Requirements, and the reasoning that is not negotiable:

- **`StyledProperty<IReadOnlyList<LayerZone>?> Zones`**, and `StyledProperty<int> SelectedPart` (default -1).

  Register both so a change calls `InvalidateVisual`; `PmtZoneEditorControl` shows how.
- **Draw, per lane:** the lane's background (alternating subtly so sixteen rows are countable), the part's
  zone, its label and tone name, and the selection outline when `SelectedPart` matches.
- **Draw, across the chart:** vertical grid lines at each C with `MidiNote.Name` beneath, and heavier lines at

- **Draw fades** as a gradient from transparent to the zone's fill across `KeyFadeLowerWidth` at the low edge
  and `KeyFadeUpperWidth` at the high edge, and the velocity equivalents vertically. A part with a fade must
  not look like a hard split, because the whole value of this chart is showing where parts really overlap.
- **Every brush from a resource.** `App.axaml` has the `Sn*` set; grep it. No inline colours — the rule is in
  the memory note `no-hardcoded-colors-in-xaml` and applies to code-created brushes too. `PmtZoneEditorControl`
  shows how a control reaches resources.
- **No `ToolTip`, anywhere.** A tooltip is a popup and it swallows clicks on the control it describes; this

- Sixteen lanes over a realistic height is ~20px per lane. Say in a comment what minimum height the control

### Task 3: The control, interaction

**Files:**

- [ ] **Step 1: Add the three events and the drag**

Three events, so the control stays ignorant of view models:

```csharp
    /// <summary>A zone was dragged. Carries the whole new zone rather than a delta, so the handler writes
    /// values and does no arithmetic.</summary>
    public event EventHandler<LayerZoneEditedEventArgs>? ZoneEdited;

    /// <summary>A zone was double-clicked: show that part's own tab.</summary>
    public event EventHandler<LayerPartEventArgs>? ZoneActivated;

    /// <summary>A point in a lane was pressed: audition that part at that key and velocity.</summary>
    public event EventHandler<LayerAuditionEventArgs>? AuditionRequested;
```

with small `EventArgs` classes in the same file.

**The drag.** Copy `PmtZoneEditorControl`'s `_dragPart`/`_dragHandle`/`_dragOrigPos` shape. `Left`/`Right` move
the key range, `Top`/`Bottom` the velocity range, `Body` shifts the whole zone in both axes. Clamp with
`PmtZoneMapping.Clamp`, and do not let lo cross hi — decide which of the two rules you want (block, or swap)
and write down which, because a zone whose lo exceeds its hi is a zone the instrument reads as silent.

**The undo gesture.** Wrap the drag in a `PointerGesture` (`Src/Controls/PointerGesture.cs`): `Begin` at press
with the captured element, `End` at release. **Do not hand-roll the capture-lost handling** — the event is
Direct and reaches only the element that held the capture, `PointerGesture` already knows that, and the last
implementation written from scratch got it wrong. Capture the pointer on the control at press
(`e.Pointer.Capture(this)`) so `e.Pointer.Captured` is this control and the drag survives the pointer leaving
it.

**The audition.** On press, before deciding about a drag: raise `AuditionRequested` with the part from the lane,
`KeyAt(x)` and `VelocityAt(part, y)`. Fire it for a press anywhere in a lane, including outside the part's own
zone — a silent answer is the map working. Do **not** fire it on an edge press, which is a drag and not a
question.

**Double-click.** Avalonia gives `e.ClickCount` on `PointerPressedEventArgs`; 2 means raise `ZoneActivated` and
start no drag.

## Known limitations to state in the commit messages

- **Fade widths are drawn, not dragged.** The four knobs are on the part's Set Part tab, which the map's
  **Edit fades…** button reaches. Dragging them would mean a second handle on an edge already a few pixels
  wide, four times per part.
- **A lane is about 20px tall**, so the velocity handles are small. If that proves fiddly, the answer is a
  taller chart or a zoom, not thinner handles.
- **Keyboard and wheel edits are not one gesture**, as everywhere else in this application: they arrive as
  single changes with no press or release to delimit, so they coalesce on the journal's clock.
- **The map shows the Studio Set's own key and velocity ranges**, not a tone's internal PMT zones. A PCM Synth
  tone splits its four partials by key and velocity too, and that is what `PmtZoneEditorControl` draws on the
  part's own tab. Both are real and they compose; this chart is the outer one.
